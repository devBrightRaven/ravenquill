# 台灣寫作 glossary

跨寫作 skill 通用的 hard rules 與用字對照表。**所有寫作 skill 在 SKILL.md 與 harness 檢查腳本中都應引用此檔**。

新 regex 只有在 `should flag` 與外型相似的 `should allow` 行為測試都成立後才可上線。誤報出現時收窄或撤換規則，保留回歸測試。

> 這份 glossary 是針對**台灣繁體中文**語境調校的。如果你的目標語境是別的（中國大陸簡中、香港繁中、純書面學術中文），把 §2 的對照表整段換成你那邊的判準即可，方法論不變。

## §1 標點與排版

### 1.1 標點全形強制

中文行文優先用全形標點。機械檢查目前擋中文相鄰的 `, : ? ( ) ; !`；半形句點 `.` 誤報邊界尚未證明，保留人工判斷。

| 全形（正確） | 半形（禁用） | 用途 |
|------------|------------|------|
| `，` | `,` | 逗號 |
| `。` | `.` | 句號 |
| `：` | `:` | 冒號 |
| `；` | `;` | 分號 |
| `？` | `?` | 問號 |
| `！` | `!` | 驚嘆號 |
| `「」` | `""` | 引號（中文用「」，不用 ""） |
| `（）` | `()` | 括號（中文文意用全形） |

**例外**：純英文句、程式碼、檔名、URL、版本號（4.7、v1.2、settings.json）保留半形。

**為什麼**：半形 `,` 在中文行文中看起來怪、不專業，是 AI 預設輸出的明顯指紋之一。

**驗收**：`check_halfwidth_punct()` 檢查中文相鄰的 `, : ? ( ) ; !`，排除 URL、code fence、inline code 與數字夾點。

#### 1.1.1 對外短訊分號（`audience: external` + `type: client-message` gate）

對外短訊（即時通訊／客戶訊息等 `type: client-message`）全形「；」一律改句號斷句；對外長文用分號列舉合理，故只 gate 短訊、不擋長文。

**設計理由**：短訊讀者滑訊息時間有限，分號列舉的閱讀負擔比長文高；長文分號列舉是正常書面用法，不應誤殺。

**邊界**：只檢查 prose；code fence、inline code、縮排 code、blockquote 與引用原話不算草稿本文。

**驗收**：`check_message_semicolon()`（`taiwan-style-check.py`），需先 `parse_frontmatter()` 判斷 `type: client-message` 才 gate。

### 1.2 重複長橫線「——／──」禁令（hard rule）

機械檢查擋連續兩個長橫線 `——` 或 `──`。單個 `—`、ASCII `--` 與其他線號目前不硬擋，需按語境人工判斷。

**怎麼改**：逐處判斷取代：
- **句號**：前後是完整意思可以獨立站的兩句 → 拆兩句
- **逗號**：前後是輕度補充或連接 → 改逗號
- **冒號**：後面是前面的展開、舉例、定義 → 改冒號
- **括號**：後面是補充解釋或插入語 → 用全形括號（）
- **重寫**：上面都不適合 → 重寫句子保留原意

**為什麼**：破折號是 AI 生成中文最氾濫的連接符，過量使用會讓行文有明顯的「機器節奏」。

**驗收 regex**：`——|──` 命中即違規。

## §2 用字遣詞（大陸 → 台灣）

> 以下對照表是台灣語境判準。換語境時整段替換。

### 2.1 詞彙對照（腳本硬擋）

> 本表進 `taiwan-style-check.py` 的 `MAINLAND_WORDS` 硬擋。增刪須同步該腳本。
> 「該不該硬擋」的判準：**台灣有同形詞但意思不同、或字形明顯異樣 → 真陸味，擋**；台灣本來就這樣用 → 風格偏好，移到 §2.1.3 不擋（誤報率與台灣人敏感度高度負相關，越會誤報的越不該硬擋）。

| 大陸用語 | 台灣用語 | 觸發語境 |
|---|---|---|
| 範式轉換 | 典範轉移 | paradigm shift 譯名 |
| 視頻 | 影片 | 多媒體 |
| 視頻號 | 短影音帳號 | 社群媒體 |
| 公眾號 | 粉專／帳號 | 社群媒體 |
| 在線 | 線上 | 數位狀態 |
| 網絡 | 網路 | internet |
| 互聯網 | 網路 | internet |
| 批量 | 批次 | 量化處理 |
| 軟件 | 軟體 | software |
| 信息 | 資訊 | information |
| 默認 | 預設 | default |
| 鏈接 | 連結 | link |

#### 2.1.1 科技詞（硬擋）

> 來源：2025 版兩岸 3C 用語對照表坐實，全部低誤報。台灣用語為主。

| 大陸用語 | 台灣用語 | 觸發語境 |
|---|---|---|
| 屏幕 | 螢幕 | 顯示器 |
| 硬盤 | 硬碟 | 儲存裝置 |
| 硬件 | 硬體 | hardware |
| 服務器 | 伺服器 | server |
| 登錄 | 登入 | login |
| 操作系統 | 作業系統 | OS |
| 數碼 | 數位 | digital |
| 攝像頭 | 鏡頭／視訊鏡頭 | webcam |

#### 2.1.2 商業黑話（硬擋；只擋重黑話）

> 痛點／落地／優化／賽道已入台籍故**放行**，只擋下列明顯黑話味的詞，並給台灣替代。

| 大陸黑話 | 台灣替代 | 觸發語境 |
|---|---|---|
| 賦能 | 增能／強化能力 | enable／empower |
| 復盤 | 檢討／事後回顧 | retrospective |
| 對標 | 對照／標竿 | benchmark（「標竿學習」是台灣管理正式詞） |
| 抓手 | 著力點／切入點 | handle／lever |

#### 2.1.3 風格偏好（glossary 提醒，腳本不硬擋）

> 下列非純陸味，台灣亦通用，硬擋會誤傷（grep 無法判語境）。寫作自行斟酌，**不收進 `MAINLAND_WORDS`**。

| 詞 | 偏好台用 | 為何不硬擋 |
|---|---|---|
| 數據 | 資料 | 台灣全通用、教育部辭典有收（數據顯示／行車數據），data 雙譯 |
| 項目 | 專案（限 project 義） | 「服務項目／檢查項目／項目符號」是 item 義台灣本詞 |
| 文件 | 檔案／文件（看語境） | file 用檔案、document 用文件，台灣兩義並用 |
| 用戶 | 使用者／用戶 | 兩者皆台灣慣用 |
| 平臺 | 平台 | 字形差異（臺 vs 台），「臺」為台灣官方正體，不宜擋 |
| 質量 | 品質（quality 義） | 物理 mass 是正式用語，regex 無法分辨 |
| 閉環 | 完整循環／收尾閉合（商業義） | closed-loop 控制是工程用語 |
| 顆粒度 | 細緻度／粒度（商業義） | 技術 granularity 有合理語境 |

### 2.2 動詞 audit 表（最常踩雷）

寫完後逐動詞掃過，比對下表：

| 偏大陸 | 台灣用語 | 觸發情境 |
|---|---|---|
| 接下（任務／事情） | 接下來／接住 | 「把每件事都接下」→「接下來」 |
| 一條條清掉 | 一條條打掉 | 證據／障礙 |
| 對接 | 接洽／對應／串接 | 客戶接洽、跨部門對應 |
| 推來的案子 | 找上門的案子／接到的案子 | 業務情境 |
| 卡上的是 | 排上的是 | 排程／隊列 |
| 搞反／搞 X | 弄反／弄 X | 「搞」字在大陸用得頻繁 |
| 讀漏了 | 漏看了／漏掉 | 閱讀理解 |
| 沒細答 | 沒講細／沒交代清楚 | 訪談／書評 |
| 裁掉 | 砍掉 | 內容／段落 |
| 躺平 | 擺爛 | 失去動力的形容 |
| 自承 | 自己說／坦言 | 引用本人說法（沒有認罪語境時） |
| 撐（士氣／態度／處境等抽象主詞） | 維持／面對／走過 | 「員工士氣怎麼撐」→「員工的士氣怎麼維持」 |
| 判（判得了／判得出） | 判斷 | 書面雙字動詞砍成單字，偏書面又不自然：「電腦判得了」改「電腦可以判斷」 |
| 驗（驗得出／驗得到） | 驗證 | 同上；但口語自然的單字動詞保留：「抓得到／改一下／跑一次」不算病，勿過度雙字化 |

### 2.3 動詞通則（從上表抽出）

1. **「撐」用在抽象主詞**（士氣、態度、處境）→ 換「維持」「面對」「走過」
2. **「搞」字當動詞前綴** → 換「弄」
3. **「接 X／推 X」單字動詞接事務** → 加助詞變多字（接下來／找上門）
4. **「裁／清」當「砍掉」用** → 直接寫「砍掉」「打掉」
5. **抽象詞前的「的」不要省** → 「員工士氣」加「的」變「員工的士氣」更台灣
6. **長句句中加「，」斷氣口** → 不要兩個分句用「不是 X，是 Y」一氣到底
7. **書面化動詞**（自承、自陳）→ 沒有正式語境就用口語（自己說、坦言）

## §3 術語白話化

### 3.1 API 技術術語禁令（hard rule）

解釋技術概念給一般讀者時，不要用「打 API call」「呼叫 API」這類術語。技術文件可以保留，面向讀者的解釋一律白話。

**範例**：
- ❌ 打 API call → ✅ 在背景偷偷幫你問一個問題
- ❌ 呼叫 API → ✅ 偷偷送請求出去

**為什麼**：一般讀者覺得這種講法超難懂。

### 3.2 英文技術詞中文化（科普文／社群文）

科普文預設中文化。只有翻譯會失真的極少數詞保留原文（例：Architect、Figure 6、free-form）。

| 英文 | 中文 |
|---|---|
| ticket / bug | 任務 |
| tech guy | 科技人 |
| junior | 初階 |
| context（能力背景語境時） | 經驗需求 |
| prompt | 提示詞 |
| code | 程式碼 |
| agent | 看情境，配 Agentic AI 觀念啟蒙時保留 |

**驗收**：grep 正文英文詞密度，>1% 就 warn。

**為什麼**：科普文讀者是初學者，已經被主題墊高一層門檻，英文詞再墊一層會勸退。

---

### 3.3 對外工程黑話（writing-harness `--public`）

對外／知識資產長文（科普／客戶訊息／提案／教學講義）禁用工程黑話。對內檔（方法論／skill／內部筆記）保留這些詞合理，**只在 `--public` 模式檢查**。分兩段：

**A. regex 紅燈（`taiwan-style-check --public` 硬擋，命中即修）**

| 黑話 | 對外白話 |
|---|---|
| 機械可檢 | 規則明確／電腦抓得到 |
| false positive | 誤報 |
| verbatim | 原話完整收錄 |

**B. LLM 自審（不進 regex，避免誤殺工程客戶語境）**

下列游走詞 regex 誤報率高（多有合法他義），靠寫作前自我比對，不硬擋：

| 黑話 | 對外白話 | 為何不 regex |
|---|---|---|
| 閘／gate | 關卡／把關 | 「閘門／閘道器」合法 |
| harness | 護欄／品管機制 | 「馬具／安全帶」本義 |
| 棘輪／ratchet | 只升不降 | 機械本義合法 |
| sub-agent | 子代理／分身 | 視對象 |
| 正則／regex | 規則比對 | 罕見但有他義 |
| pipeline | 產線／流程 | 已半通用 |
| 固化 | 內建／定成規矩 | 材料／化學語境合法 |

**為什麼**：工程黑話對一般受眾是術語牆。對外產出若少了「黑話轉白話」這層，就會變成每次都要跟一般人重新解釋。封閉純黑話做機械閘（紅燈）；游走詞靠判斷（呼應 §2.2 動詞 audit 的 context-dependent 設計）。

### 3.4 對外口語化補充（S2 人工判斷）

源於一則對外客戶回顧訊息的真實糾正：S1 過了，但真人一讀就抓到 ①「用字不夠台灣」（成語／被動）②「信任感馬上就掉」太像 slop（X 感抽象名詞）。

**A. 書面成語／連接詞**：按受眾、場景與句子判斷，不假設所有成語都是壞文字。

| 書面成語 | 對外白話 |
|---|---|
| 大同小異 | 差不多／都那幾樣 |
| 不外乎 | 不就是／大概就是 |

**B. 抽象名詞「X 感」**：當詞句沒有說明人物、動作或後果時，改成具體場景；「安全感」「信任感」等普通合理用法不因字面自動判錯。

**為什麼不硬擋**：兩類詞都有大量合理用法，單純子字串 regex 無法提供有意義的 should-not-flag 邊界。

## §4 句型與結構

### 4.1 「不是 X，是 Y」否定翻轉句型

**規則**：文案寫作禁止「不是 X，是 Y」「不需要 X」「他不是 X，他是 Y」等先否定再翻轉的 AI 慣性句型。直接講正面事實。

**範例**：
- ❌「不是範本，是根據你的業務做的」→ ✅「根據你的業務，從頭做出來的那一個」
- ❌「他不是工程師，他是⋯」→ ✅「他是⋯」
- ❌「不需要寫程式碼」→ ✅「用對話就能完成」

**密度上限**：同一篇文章用超過 2 次「不是 A，是 B」就要輪替：
- 「不見得 A，他們只是 B」
- 「而是」加轉折
- 「並不代表」＋補說明

**為什麼**：先假定一個事實，再突破直覺認知，最後給答案——這個結構太 AI 了。機械重複會讓文章的結構感壓過內容，像 AI slop 的二元對比模板。

**驗收 regex**：`不是.{1,15}?，而?是` 出現次數 > 2 就換句。

### 4.2 因果段補連接詞，不只靠冒號硬接

寫因果邏輯時，不要只用冒號跳到結果。補「因為／才／所以」讓讀者跟上。

**範例**：
- ❌「是有 Architect 這種角色：⋯⋯」
- ✅「但因為有 Architect 這種角色：才讓執行的結果被放大。」

**為什麼**：冒號適合列舉或定義，不適合因果推導。純冒號跳接是邏輯鬆的訊號。

### 4.3 段落標題優先主述句，少用否定懸念

段標題偏好「變快並非紅利」（主述肯定）勝過「紅利不是變快」（否定懸念）。

**為什麼**：否定句型有被動感、像社群鉤子放在正文段標出戲。主述句更有主張感，讀者一眼看到結論。

## §5 動詞血肉與收尾

### 5.1 收尾保留動詞，不為 punch line 抽掉具體動作

具體動詞（採坑／優化／刪掉重來）比抽象名詞（使用經驗）更能落地。

**規則**：收尾前檢查，原始素材裡的具體動詞要保留至少 60%。把 3 個動詞濃縮成 1 個抽象名詞，視為損失。

**為什麼**：把「採坑、優化、刪掉重來」抽象成「使用經驗」會丟掉三個動詞。抽象金句讀者無感，動詞能看見畫面。

## §6 驗收 hook regex 建議

寫作 skill 完稿後跑下列檢查（`scripts/taiwan-style-check.py` 已實作大部分）：

| 檢查項 | regex／方法 | 違規處理 |
|---|---|---|
| 半形標點 | `[一-龥]\s*[,\.\:;\?\!]\s*[一-龥]` | 全部換全形 |
| 重複長橫線 | `——\|──` | 取代或重寫 |
| 「不是 X，是 Y」密度 | `不是.{1,15}是` count > 2 | 換句型 |
| 英文詞密度（科普文） | 半形英文詞／總字數 > 1% | 中文化 |
| 動詞 audit | 比對 §2.2 表逐詞掃 | 換台用動詞 |
| API 術語 | grep `API call\|呼叫 API\|API 呼叫` | 換白話 |
| 大陸用語 | 比對 §2.1 表 grep | 換台灣用語 |
| 結論引導／雜訊框架詞 | `taiwan-style-check.py` 的 `CONCLUSION_LEAD_NOISE`（句首雜訊詞 + 定型句 + 「很／非常／更…直覺」族 AI Slop） | 重寫，不把判斷塞給讀者 |

各 skill 在 harness 階段把上述檢查包成 Python／JS function，命中報告位置 + 建議改法。
